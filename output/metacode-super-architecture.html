01总体架构:三层 + 一条总线

metacode super(代号 cc-zig)是 Claude Code 的 Zig 实现。它的核心架构信条是把"做事的引擎"和"展示/交互的外壳"彻底切开,中间只留一条可序列化的事件总线。这让同一个引擎能驱动 TUI、headless CI、未来的 GUI / 语音前端,而引擎本身对此一无所知。

层位置知道什么不知道什么
外壳层UIrepl/ app.zig终端字节、键盘、provider 选择—
协议总线PROTOcore/protocol/纯数据契约(事件/请求)谁渲染、谁是 provider
内核层COREcore/ api/turn 循环、工具、上下文终端、渲染、wire 协议

02TUI 与 Agent Loop 如何分离

分离不是约定,是编译器强制的物理边界。内核打包成独立库 metacodes-core(src/lib.zig),它能编译通过本身就证明了它没有偷偷依赖任何 UI 代码。

分离的三个支点

  • vtable 物理边界:UiBackend 是 {ctx, emit, poll},实现住在 UI 端,内核只持接口
  • 事件纯数据:CoreEvent 全是值/slice,零函数指针、零共享态 → 可序列化、可跨进程
  • 表达权上移:内核无条件 emit,backend 据事件 tag 自决渲染。core 不问"这个工具该不该显示进度卡"

编译期证明 build.zig · test:lib

// src/lib.zig — 库根
test {
  // 引用全部 re-export → 强制编译每个
  // 模块。若任何 core 模块间接拉到
  // repl/tui/app,路径不存在 → 编译失败。
  testing.refAllDecls(@This());
  testing.refAllDecls(protocol);
}

zig build test:lib 绿 = core 与 UI 物理隔离的机器证明。

实测事实 agent_loop.zig 的 import 清单只含:中立类型(types/json/conversation)、Provider vtable、Permission、StreamHandle、协议头(protocol/ui_backend、protocol/ui_event)。没有任何 repl/ / tui/ / app 的 import。所有"怎么显示"的决策都通过 backend vtable 上移到了 UI 端。

core 与 UI 唯一的可变共享点:AbortSignal

除了 emit(只读数据出)和 poll(只读数据入)两条纯数据通道,core 与 UI 之间唯一的 mutable 共享是 AbortSignal——一个原子标志位。SIGINT handler 或 watcher 的 ESC 键直接 .abort() 它,run() 在轮头和流事件前 isAborted() 检查。这是有意收窄的:把共享态压到一个原子 bool,消除了 core/UI 之间所有其他竞态可能。

03Agent Loop 接口详解

这是整个系统的引擎入口。理解了 run() 的签名、Options 的能力面、StopReason 的退出语义,就理解了内核能做什么、不能做什么。

run() 签名 agent_loop.zig:248

pub fn run(
    conversation:   *Conversation,                   // 对话树(原址追加 assistant/user 块)
    provider:       Provider,                         // LLM 后端 vtable(本报告"多 Provider"部分)
    tool_defs:      []const ToolDefinition,            // 工具定义(权限/池过滤/能力门控共用)
    permission_ctx: *const PermissionContext,         // 权限决策 + session 记忆 + 询问回调
    opts:           Options,                          // 运行选项(见下,38 字段)
    backend:        *const UiBackend,                  // UI vtable:emit(CoreEvent)+poll(UiEvent)
    allocator:      std.mem.Allocator,                // turn 作用域分配器
) !RunResult

七个参数划出三条清晰的边界:conversation 是状态(输入输出原址);provider / backend / permission_ctx 是三个vtable 注入点(LLM 后端、UI 前端、权限策略各自可换);opts 是能力开关面板。引擎本身不持有任何这些东西的所有权,全是借用——这让它天然可重入、可并发(每个 subagent 一次独立 run)。

Options 不是杂物袋,而是引擎的能力注入面。所有字段默认 null/零值——意味着最小可用引擎只需 conversation + provider + 三个 vtable,其余全是渐进增强。下表按职责归组:

职责边界:opts.api_client ≠ run() 的 provider 参数 provider(第 2 参数)是引擎"用"来发请求的;opts.api_client 是工具/subagent 拿去"构造 per-call client"的。前者是消费,后者是工厂。两者职责不同,刻意分开——这是 P1 重构时 Linus 确认保留的设计。

resumeRun() 与挂起/恢复 agent_loop.zig:924

RunResult.stop_reason == .suspended 时携带 SuspendInfo(pending tool_use_id + 渲染规格 + 同轮已完成工具的结果)。调用方落盘 + 投递异步前端,响应到达后调 resumeRun()。

L3 的致命约束:同 turn 配对 Anthropic API 要求每个 tool_use 必须在紧接的同一条 user 消息里有对应 tool_result,不能拆成两条。所以挂起时不能提交任何 partial user 消息——已完成工具的结果 stash 进 completed_results,等 resumeRun 把"迟来的 pending 结果 + 所有 stash 结果"一次性放进单条 user 消息。这是 Linus review 抓出的 bug,多工具测试证明。这个能力 cc(TypeScript)本身没有——是 cc-zig 超越 cc 的点。

04协议层:CoreEvent / UiRequest

协议层是分离的合同。它有两种通信形态:单向通知(CoreEvent,fire-and-forget)和同步请求(UiRequest,要等用户答复)。

UiBackend — 仅两个方法 protocol/ui_backend.zig:28

pub const UiBackend = struct {
    ctx:  *anyopaque,
    emit: *const fn(ctx, session: SessionId, ev: CoreEvent) void,   // core→UI 单向通知
    poll: *const fn(ctx, session: SessionId) ?UiEvent,         // UI→core 非阻塞(中断/入队消息)
};

CoreEvent(节选)ui_event.zig:40

  • text_chunk / stream_begin / stream_done — 流式文本
  • tool_start / tool_progress / tool_result — 工具生命周期
  • set_current_tool / clear_current_tool — spinner 喂料
  • usage(含 cache_read/cache_creation)— token 计数
  • auto_compact / retry_notice — 系统通知
  • ui_request_pending — L3 异步挂起信号
  • diag_*(6 种)— L4 诊断 span 树(DiagnosticsBackend 专用)

UiRequest — 同步请求 ui_request.zig:19

  • permission — 工具权限确认
  • ask_question — AskUserQuestion 多选
  • plan_approval — ExitPlanMode 计划审批
  • custom — L2 动态 UI(opaque passthrough)

返回 RequestOutcome 三态:answered(同步前端即答)/ pending(异步前端 out-of-band)/ unavailable(headless 兜底)。

为什么 emit 无条件发? agent_loop 不做"这个工具要不要显示卡"的判断——它无条件 emit tool_start/tool_result,由 backend 据工具名自决渲染(TUI 把 Bash/Read 渲成动态卡,Edit/Write 渲成 diff,headless 全转 JSON)。表达权完全在 UI 端,core 零渲染知识。

05后端实现矩阵

同一套 UiBackend 协议,五种实现,覆盖从交互式终端到 CI 到可观测性的全场景:

后端位置emit 策略poll场景
TuiBackendrepl/tui/映射 RenderRegion:文本→scrollback,工具→卡MsgQueue + AbortSignal主交互
WriterBackendcore/参数化 sink,仅 text/color/verbose恒 nullheadless/后台/单测
HeadlessBackendcore/每事件序列化成 NDJSON 行恒 nullCI/进程间/回放
DiagnosticsBackendcore/只消费 diag_*,累积 span 树—可观测性(L4)
TeeBackendcore/decorator:转发 primary + secondary仅 primary主+诊断并存
分离的红利 WriterBackend/HeadlessBackend/DiagnosticsBackend 全住在 core/ 而非 repl/——因为它们不碰终端。只有 TuiBackend 在 UI 层。这条边界让 mock backend 能驱动真 agent_loop 跑全链路测试,无需终端。

06输入 / tick / 中断的归属

"谁拥有键盘和定时器"是分离架构最容易渗漏的地方。cc-zig 的答案:全归 backend,core 零参与。

键盘输入

TuiBackend owns 一个生成期 stdin watcher 线程(startInput/stopInput,由 loop.zig 在 run() 前后编排)。agent_loop 完全不碰 stdin。

Spinner tick

没有独立 ticker 线程。watcher 的 poll(timeout=100ms) 超时即推进 spinner 动画——单线程一石二鸟。GUI 后端可换成 requestAnimationFrame。

中断

AbortSignal 是 core/UI 唯一共享态。SIGINT / ESC 直戳它,run() 轮头与流事件前 isAborted()。其余全是只读 emit/poll。

07多 Provider 缓存:为什么需要专门设计

Prompt caching 是 coding agent 成本与延迟的命门——system prompt + 工具 schema 每轮重发,缓存命中能省 50–90% 输入 token 成本。但三家的缓存机制从控制方式到生命周期到计费全不一样,不能用一个 cache: bool 糊弄过去。

核心张力 Anthropic 要你显式打断点(请求体里塞 cache_control);OpenAI 全自动(你啥都不能标,只能调整 prompt 结构);Google 给你两种模式(隐式自动 + 显式创建一个有句柄、有 TTL、会 404 过期的 cache 对象)。一个统一抽象必须同时容纳"我标断点"、"我什么都不做"、"我管理一个带生命周期的远程对象"三种范式。

09缓存抽象与扩展点设计

设计原则承袭整个 Provider 架构:缓存是 provider 的私事,不上浮到内核。agent_loop 不知道缓存存在,它只发中立请求;每个 provider 在自己的序列化层把缓存策略翻译进 wire 格式。但三家差异大到需要一个显式的扩展点契约,而不是各 provider 各写各的。

图 4 · 缓存扩展点:两个 hook 容纳三种范式。Anthropic 注入断点 / OpenAI 几乎 no-op / Google 管理有状态句柄。内核完全无感

建议的扩展点契约(挂在 Provider 上)

// 缓存策略是 provider 私事,但契约统一。两个 hook 容纳三家范式:
pub const CacheHooks = struct {
    // 请求序列化前调用:provider 据自己的范式改写请求(打断点/建对象/no-op)。
    // 返回中立的"本请求缓存意图",由各 provider 序列化层消费。
    prepareCacheFn: ?*const fn(ctx, *RequestPlan) anyerror!void = null,

    // 流结束读 usage 时调用:provider 解析自己字段名的缓存命中数,归一成中立 UsageDelta。
    // (已有:UsageDelta.cache_read_input_tokens / cache_creation_input_tokens 两中立字段)
    onUsageFn:      ?*const fn(ctx, raw_usage: []const u8) UsageDelta = null,
};

为什么是这两个 hook?

  • prepareCache 是"写"侧:三家在此分叉(注入断点 / no-op / 建对象+查表)
  • onUsage 是"读"侧:三家字段名不同(cache_read_input_tokens / cached_tokens / cachedContentTokenCount),归一成已有的中立 UsageDelta
  • 内核只消费中立 UsageDelta,通过 CoreEvent.usage 上抛 UI——缓存命中显示与 provider 无关

Google 的有状态难点放哪?

Google 需要一张 {prefix_hash → cache_name, expire_time} 句柄表 + 404 重建逻辑。这张表属于 GeminiClient 实例私有,不上浮。prepareCacheFn 内部查表/重建,对外仍只暴露统一契约。TTL 主动续期可挂在 client 的后台 tick。

扩展点设计纪律(承袭 P3 教训) 契约现在只为已验证的 provider 落实现:Anthropic 的 prepareCache 已是 request.zig 里的 cache_control 注入(实证),OpenAI 的是 no-op + 命中读取。Google 的 hook 先留签名不留空实现——绝不在契约里声明未接线的能力制造"看起来支持"的假象。等真写 GeminiClient 时再据实填,配 L2 端到端测试(MockServer 喂 Gemini 格式 → 断言句柄复用)。

一句话总结

分离:内核 agent_loop 通过 UiBackend 纯数据总线与终端解耦,编译期 test:lib 证明 core 不可达 UI;唯一可变共享是一个 AbortSignal 原子位。缓存:三家机制(显式断点 / 全自动 / 有状态对象)差异巨大,但都收进 provider 的两个 hook(prepareCache 写侧分叉 + onUsage 读侧归一),内核与 UI 对"现在用哪家的缓存"一无所知,也不需要知道。
