01问题:为什么单 SDK 不够

参考实现 Claude Code(TypeScript)把所有后端归一成 Anthropic SDK 的形状。这在只服务一家模型时干净,但一旦要支持异协议后端就成了债务。

现实约束摆在桌面上:Anthropic 走 /v1/messages + 自有 SSE 事件名;OpenAI 走 /v1/chat/completions + choices[].delta 增量;Gemini、Grok 各有一套;认证有的是 API key,有的 OAuth,有的是企业中转站。如果让 agent loop 直接认识这些差异,每加一个后端就要改内核——这是 cc 把 supports_web_search 之类判断散落进各工具(if (provider==vertex && model.includes('opus-4')))的同类病。

设计目标 agent_loop / Conversation / 中立 IR 一行不改,就能接入讲完全不同 wire 协议的后端。新后端的全部脏活(协议 / 认证 / URL / SSE 格式)锁在它自己的实现文件里,内核对它们零感知。

02核心原则:中立 IR 是归一点

整个架构建立在一个判断上:不是抽象后端,而是抽象后端两端的数据。请求侧用中立的 ApiMessage / ToolDefinition;响应侧用中立的 StreamHandle(吐 StreamEvent)+ ApiResponse。每个 provider 在自己实现内部把中立 IR 翻译进/出它的 wire 格式。

图 1 · 内核只在中立 IR 上工作;每个 provider 自己翻译进/出 wire 格式
关键推论 加一个后端 = 写一个新的翻译器,而不是改内核。翻译器是 leaf 模块,谁都不依赖它,它只依赖中立 IR。

04Provider vtable:type-erased,非 generic

接口形状刻意镜像项目里已验证的 UiBackend:一个 ctx: *anyopaque + 一组函数指针。这不是 OOP 习惯的复刻,而是一个有意的工程取舍。

pub const Provider = struct {
    ctx: *anyopaque,                          // 后端实例的 type-erased 指针

    modelFn:            *const fn(ctx) []const u8,
    sendStreamFn:       *const fn(ctx, msgs, system, tools, abort, …) anyerror!StreamHandle,
    sendStreamRetryFn:  *const fn(…, max_retries, retry_base_ms, reporter, …) anyerror!StreamHandle,
    sendFn:             *const fn(ctx, msgs, system, tools) anyerror!ApiResponse,  // 非流式 (compact)
    maxTokensFn:        *const fn(ctx) u32,
    maxInputTokensFn:   *const fn(ctx) u32,          // auto-compact 阈值用
    supportsFn:         *const fn(ctx, cap: Capability) bool,

    // 便利转发:provider.sendStream(...) 内部 → self.sendStreamFn(self.ctx, ...)
    pub inline fn sendStream(self: Provider, …) anyerror!StreamHandle { … }
};

为什么不用 generic?

最初的尝试是 fn run(provider: anytype)。但 generic 会把 provider 的具体返回类型(如 client.StreamResponse)渗进内核签名——内核反向依赖实现层,形成循环依赖,Zig 编译期就炸。

vtable 把返回类型也归一成中立的 StreamHandle(住在 leaf 层 api/stream.zig),接口里不出现任何 provider 具体类型 → 无循环、无 generic 膨胀。

认证为何不抽接口?

OAuth / SigV4 / 企业中转站差异太大,强抽一个 Auth 接口只会得到一个谁都不合身的抽象。

决策:认证是每个 Provider 实现的私事,塞在 sendStream 内部(Anthropic 用 x-api-key,OpenAI 用 Authorization: Bearer)。对齐 cc——它也没抽 Auth。

05StreamHandle:响应侧的归一

请求侧归一相对容易(消息/工具都是数据)。难点在流式响应——两家的 SSE 事件结构完全不同。解法是把流也做成 type-erased vtable:内核反复调 handle.next() 拿中立的 StreamEvent,完全不知道底层在解析哪家的字节。

pub const StreamEvent = union(enum) {
    text:              []u8,              // 助手文本增量
    tool_use_start:    ToolUseResult,     // {id, name, input_json} — owned
    web_search_result: WebSearchResultEvent,
    web_search_query:  []u8,
    usage:             UsageDelta,
    done:              void,
};

pub const StreamHandle = struct {
    ctx:          *anyopaque,
    nextFn:       *const fn(ctx) anyerror!?StreamEvent,   // null = 流尽
    deinitFn:     *const fn(ctx) void,
    stopReasonFn: *const fn(ctx) StopReason,
    requestIdFn:  *const fn(ctx) RequestId,             // 日志串联,契约:必须有效
};
同一个 union,两种字节来源 Anthropic 的 content_block_delta(input_json_delta) 跨多个 SSE 事件累加 → tool_use_start;OpenAI 的 choices[].delta.tool_calls 跨 chunk 累加 → 同一个 tool_use_start。内核看到的事件序列完全一致,这就是"换 provider 一行不改"的物理基础。

07Capability 表:能力门控的单一真相源

不同后端能力不同:Anthropic 有 server-tool web search,OpenAI 没有;OpenAI 有 structured output,旧 Claude 没有。cc 把这些判断散落各处。本架构集中成一张 [ProviderKind][model] → Capability 的表,内核只问 provider.supports(cap),绝不自己 if(model.includes(...))。

CapabilityAnthropic (Claude 4.x)OpenAI (gpt-4o)门控行为
web_search✓ 全模型✗OpenAI 下 WebSearch 工具自动从请求 tools 数组剔除
structured_output✓ 4.x✓ function calling—
prompt_cache✓✗不发 cache_control
extended_thinking✓ 4.x / 3.7✗—
server_tool✓✗—
门控是真消费者,不是空壳 requiredCapability(tool_name) 把工具映射到所需能力(WebSearch → web_search)。agent_loop 在发请求前扫一遍:若某工具需要的能力当前 provider 不支持,就从发给模型的 tools 数组剔除(对齐 cc 的 isEnabled)。这个剔除还接进了 cache-fingerprint hash,保证请求体与缓存键一致。P3 端到端验证:OpenAI 跑起来后 WebSearch 确实从请求体消失,Read 还在。

08组装层:全仓唯一的 if(provider)

内核和 UI 对 provider 差异零感知的代价,是把所有差异收敛到一处——App 组装层。这是有意为之的"脏区隔离":差异不是消失了,而是被关进一个笼子。

// src/app.zig — 整个多 Provider 架构里唯一的 if(provider)
pub fn provider(app: *App) Provider {
    return switch (app.config.provider_kind) {
        .anthropic => app.api_client.provider(),
        .openai    => app.openai_client.?.provider(),
    };
}

// main.zig — 选择来源:env 显式 > model 前缀推断
if (getenv("METACODES_PROVIDER")) |v| { if (eql(v,"openai")) kind = .openai; }
else kind = inferProviderKind(model);   // gpt* / o1* / o3* → openai

内核侧的 6 个调用点(REPL / headless / subagent 驱动)统一从 app.api_client.provider() 改成 app.provider()。内核拿到的永远是中立 Provider,不知背后是谁。

Linus 抓到的真 bug — 死资源的活副作用 App 同时持有 api_client(Anthropic,永远构造)和 openai_client?(可选)。最初 probeModels() 无条件跑——OpenAI 模式下它对着 Anthropic 的 /v1/models 端点用真 key 发真请求。修复:probeModels / setMaxTokensOverride 整块 gate 进 if (provider_kind == .anthropic)。教训:死资源不等于无害,它的初始化副作用照样会触发。

09所有权契约与陷阱

Zig 没有 GC,跨 vtable 边界的内存所有权必须显式约定。这里有两个用血换来的契约。

契约一 · StreamEvent 是 move,不是 borrow tool_use_start 的 id/name/input_json 是 owned slice,内核接管所有权(不 dupe,后续随 tool_uses 释放)。OpenAI 实现起初借用了流内部的 ArrayList → stream.deinit 和内核各 free 一次 = double-free,测试直接 ABRT。修复:flushPendingToolCall 用 toOwnedSlice 转移所有权,留下空 ArrayList(deinit 安全 no-op)。
契约二 · StreamHandle 同步消费,底层须活得久 handle 的 ctx 借用底层 StreamResponse;底层必须比 handle 活得久。Provider 值本身是廉价的(fn-ptr + 指针),按值传,但不可存进比 ctx 长寿的容器,否则 UAF。
no silent caps — 自定的死罪 OpenAI 并行 function calling 一个 delta 能带多个 tool_call,但 MVP 累积器是单组。最初的实现静默丢弃第二个——项目 CLAUDE.md 明令禁止 silent truncation。修复:双路检测(单 chunk 内 countOccurrences("index")>1 / 跨 chunk 新 id)→ log.warn 一声并只执行首个。配套测试"先红后绿"(第一版 ordering 写错导致首个工具也丢,被测试逮住),证明测试有牙齿。

10诚实边界:已做与未做

P3 的 OpenAI provider 是架构证明,不是生产级客户端。把"没做什么"说全,和把"做了什么"说全同等重要——文件头逐条登记,不制造"看起来支持"的假象。

✓ 已兑现

  • 同一 agent_loop 喂 OpenAI provider 跑通到 end_turn
  • 文本流 + 单 tool_call 工具循环跨协议
  • capability 门控:WebSearch 在 OpenAI 下自动消失
  • 组装层 provider 选择(env / model 前缀)
  • 4 component + 2 单测;全套 exit 0,0 泄漏,test:lib 绿

○ 登记未做(文件头)

  • 并行 tool_calls(warn + 只执行首个)
  • 跨 chunk arguments 转义不保证正确
  • 建连重试 / 429 退避(doStream 遇非 200 直接报错)
  • 非流式 pSend = NotImplemented → compact 退化为 keep-recent
  • max_tokens / context_window 硬编码,未按 model 区分
原则 MVP 的罪不在缺功能,在假装不缺。降级路径(如 compact 退 keep-recent)是真实存在并真会执行的兜底,不是假装的 catch。

11关键设计决策回顾

决策取舍
抽象数据而非后端中立 IR 成为唯一归一点;加后端 = 写翻译器,不改内核
vtable 而非 generic避免具体返回类型渗入内核造成循环依赖;StreamHandle 把响应也归一
认证不抽接口差异太大,留给各实现私有;避免谁都不合身的抽象
能力集中成表消灭散落各处的 if(model.includes);内核只问 supports()
差异收敛到 App 一处 switch内核 / UI 零感知;脏区隔离而非脏区扩散
诚实登记未实现项文件头逐条标注;绝不在 schema/注释里声明未接线的能力

一句话总结

把后端差异挤进两个地方——响应侧的 StreamHandle 翻译器、组装侧的一处 switch——其余所有代码(内核循环、上下文管理、工具执行、UI)对"现在跑哪家 LLM"一无所知,也不需要知道。这就是分离架构兑现的价值:同一个 agent loop,喂不同协议的 provider,跑通。
